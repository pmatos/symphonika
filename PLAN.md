# Plan: guarded "Start with provider" action backed by a durable Run-Chain Provider Plan (#861)

## Goal
Add an operator action (Issue page preview → guarded POST) that persists a chain-wide provider choice
(omp | claude | codex) in the Run Store *before* the Project's Ready Label is added, so the poll that
claims the Issue launches the first agent state with that provider. Stale/changed/blocked/reserved/
already-ready Issues are refused; a GitHub label-write failure leaves an inspectable, retryable plan.

## Assumptions
- **#855 is closed**; `issue_filters.ready_label` is the single Ready Label (`src/config-schemas.ts:130-160`, ADR `2026-10-08-1426-single-ready-label-per-project`). No legacy `labels_all` path to handle (best guess; verified closed via `gh issue view 855`).
- **"Graph fingerprint" = `WorkflowSnapshot.contentHash`** (`src/reload.ts:1493-1527`, `src/workflow/types.ts:53`). No structural graph hash exists; a comment-only edit therefore counts as "stale". Conservative and cheap; no new hashing (best guess).
- **"Snapshot identity" = the Issue snapshot row's `polledAt` + bound repository** (`ProjectIssueSnapshotRow.polledAt`, `run-store.ts:367`; `getProjectIssueSnapshotRepository`, `run-store.ts:2695`). There is no poll generation id.
- **Scope of provider application:** fresh dispatch (`run-controller.ts:1178`) *and* State Advance (`run-controller.ts:3156-3160`) use one new resolver with precedence `chain-wide plan > workflow action.provider > Project default`, because a "chain-wide" plan that silently reverts after state 1 would be a false promise. Per-state operator exceptions, provenance recording/timeline display, Continuation/PR-follow-up routing, recovery and override review stay in #862/#863/#864 (best guess).
- **Plan application at claim does not re-check the fingerprint** (epic #844: a chain-wide choice stays applicable across graph edits). The fingerprint is checked at Start time and stored for audit.
- **Start is HTML-form only** (matching `/issues/:project/:number/labels/add`, `pages.ts:1045`); no new JSON/CLI surface.
- **No silent expiry.** A plan never falls back to default routing by lapsing. `label_written` plans have no TTL (cap/host-pressure/downtime can delay a claim arbitrarily). A `pending` plan older than `PROVIDER_PLAN_PENDING_TTL_MS` (1h, lazy) becomes `expired`, which is *blocking* like `label_failed` (candidate skipped, visible on the Issue page with Cancel/Retry), never consumable. Orphans (label removed by hand, Issue closed) are surfaced and cancellable, superseded by the next Start, and skipped by claim eligibility anyway (best guess).
- **Plans are keyed by (repository owner/name, issue number)**, not Project name, because two Projects can alias one repository (`getProjectRepoAliases`, `daemon.ts:1521`); the plan row still records `project_name` for display.
- **Snapshot identity at Start = the form's `snapshot_polled_at` equals the stored row's `polledAt`.** `polledAt` changes every ~30s poll, so a stale preview is refused with "reload" (accepted false-positive; the preview page is cheap to reload). **Retry does not compare `polledAt`**; it relies on repository binding, stored-vs-current fingerprint and a fresh live eligibility read.
- Plan statuses: `pending` (persisted, label write not confirmed) and `label_written` are *consumable* by a claim; `label_failed` and `expired` are *blocking* (candidate is skipped until operator retries/cancels), because a timed-out write may have reached GitHub and a default-provider claim would be the exact bug being prevented. Terminal: `consumed`, `cancelled`, `superseded`.

## Design (condensed)
**Storage.** Table `run_chain_provider_plans(id pk, project_name, issue_number, repository_owner, repository_name, provider, graph_fingerprint, snapshot_polled_at, ready_label, status, last_error, attempt_count, consumed_run_id, created_at, updated_at)`. Partial unique index on `(repository_owner, repository_name, issue_number)` (lower-cased) `where status in ('pending','label_written','label_failed','expired')` = at most one live plan per repository Issue. Chain link: nullable `runs.provider_plan_id` set on the *root* Run at `createRun`; a chain's plan is found by a `RUN_CHAIN_ROOT_CTE` walk that reads the root Run's `provider_plan_id` **regardless of plan status** (the plan is already `consumed` when any State Advance asks), with no denormalised copy onto Continuation/Waiting/Adopted creators. Adopted chains (`providerName: null`) have no plan.

**Start protocol (daemon, `startIssueWithProvider`).** No unbounded GitHub I/O under `dispatchMutex` (ADR 0093 bounds even the `sym:claimed` write; `reconcileWaitingRuns`/shutdown-resume/stale sweep also depend on the mutex).
1. Cheap local checks, no mutex: provider in {omp,claude,codex}, `providersConfig()[provider].command` non-blank and `agentProviders[provider]` registered; `verifySnapshotRepositoryBinding` (rendered owner/repo ↔ persisted snapshot ↔ current tracker); form `snapshot_polled_at` == stored `polledAt` (Start only); form `graph_fingerprint` == live `project.workflow.contentHash` (Start; Retry compares the plan's stored fingerprint).
2. **Live read before the mutex** (with an `AbortSignal` deadline; `GitHubIssueRepositoryInput` accepts `signal`, `issue-polling.ts:15`): `tryGetIssue` + `tryGetIssueDependencies` → `normalizeIssueSnapshot` → `evaluateProjectEligibility` with the Ready Label virtually added. Refuse if the Ready Label is *already* present (snapshot or live), any `sym:*` label, excluded label, closed state, open or truncated blocker, or if the fetch fails (fail closed). Without the Ready Label nothing can race this read.
3. Acquire `dispatchMutex` for **local checks and the plan write only**: refuse on `findLiveRunIdForIssue` (in-flight, scheduled, waiting, alias-expanded; `pages.ts:3804`), `latestRunSuppressesFreshDispatch` (`run-store.ts:2431`), parked raw-FSM wait (`isIssueParkedAtRawFsmState`), or an existing live plan owned by a different in-flight Start; then one SQLite transaction supersedes any older unconsumed plan and inserts the `pending` plan. Release the mutex.
4. Add the Ready Label (bounded; reuse the add half of `writeIssueLabels` via a shared helper). Then a **conditional** state write: `update … set status='label_written' where id=? and status='pending'` (success) or `…'label_failed', last_error=…` (error). If the row is no longer `pending` (a poll already consumed it, or Cancel won) the write is a no-op and the response reports the real status. A thrown/timed-out write whose label actually landed is reconciled by Retry (live read shows label present → `label_written`).
5. Retry (`plan_id`): take `dispatchMutex` for the status flip `label_failed|expired → pending` (conditional), run steps 1-2 against the stored fingerprint with a live read, and if the Ready Label is already present mark `label_written` without rewriting; otherwise repeat step 4. Cancel (`pending`/`label_failed`/`expired`): conditional update under `dispatchMutex`; refused once `consumed`; a `label_written` plan is cancelled only by first removing the label via the existing label form (documented on the page), after which the plan shows as stranded and can be cancelled.
6. The generic add-label routes (`handleIssueLabelWrite`, bulk) still take no mutex and can add the Ready Label without a plan; that path keeps default routing and is **out of scope** (documented in the ADR). They are not made to consult plans.

**Claim boundary (poll side).** The provider is decided in `resolveAndClaim` *before* the mutex (`providerCommand`/adapter come from the loop-start `providersConfig`), so a plan must be read there. `resolveAndClaim` reads the active plan (key: repo + issue; consumable statuses only), resolves via `resolveEffectiveProvider`, and passes `expectedPlanId` (or `null`) into `claimAndPersistRun`. **Only for fresh claims (`!isContinuation`)**, inside `dispatchMutex` and before the `sym:claimed` await, re-read the active plan; id mismatch (plan appeared, was cancelled, expired or turned `label_failed`) → `FreshClaimDeferredError` (next tick re-resolves; this also covers `dispatchFresh` iterating a candidate list snapshotted before Start). Because Start/Retry/Cancel flip status under the same mutex, the check stays valid through `createRun`. Immediately after `createRun` (same synchronous block, no await) `consumeProviderPlan(planId, runId)` sets `runs.provider_plan_id` and status `consumed`; 0 rows changed → throw into the existing post-create reconcile path (ADR 0093). `pickProjectCandidate` skips candidates whose live plan is `label_failed`/`expired`, like suppressed ones. A plan whose provider has no command / no adapter is a **per-candidate** skip (not the existing `excludeProject: true`, which is right only for Project-level config): do not create a failed Run for it; the plan stays and the Issue page shows why. `pickTargetFromCandidates` (3887) filters on `agentProviders[project.agent.provider]` and must not drop a project whose default adapter is missing when the plan names a registered one (and vice versa).

## Testing
Each slice above leads with its failing test. Per repo memory, for every negative assertion ("no label write", "no plan row") first disable the guard and confirm the test fails. Prefer the daemon+HTTP seam (steps 3-4) over mocks of internals; steps 1-2 are narrow store/controller tests because the claim race cannot be forced through HTTP alone.

## Risks
- **SQLite/GitHub non-atomicity**: mitigated by persist-before-label, `pending` being consumable (crash after write, before status update) and `label_failed` being blocking + reconcile-on-retry via a live read.
- **Race: Start vs poll claim**: both hold `dispatchMutex` across their guard sections; claim re-reads the plan inside the mutex and defers on mismatch. A human adding the label by hand concurrently still lands on the plan (operator intent) or on none (deferred), never on a different plan.
- **Orphan plans** (label removed by hand, Issue closed, suppressed or blocked Issue, Project retargeted): never silently expire to default routing; `pending` > 1h becomes blocking `expired`, `label_written` stays until consumed/cancelled/superseded, keyed by repo so a retarget cannot collide. Residual: a stranded `label_written` plan can attach to a much later manual Ready Label add (operator-visible on the Issue page; accepted, documented in the ADR).
- **Indeterminate label write** (timeout, GitHub applied it): UI says "failed" while the Issue is ready; mitigated by `label_failed` being blocking and by live-read reconcile on Retry. A plan persisted but never labelled (crash between steps 3 and 4) stays `pending` and is consumable by a later manual label add within the 1h window.
- **Other writers**: generic/bulk label routes take no mutex and ignore plans (out of scope); CLI one-shot `dispatchOneEligibleIssue` (`src/dispatch.ts`, smoke only) builds its own `RunController` with no shared mutex — it does not read plans.
- **SQLITE_BUSY**: `openRunStore` has no busy_timeout; tests that open a second connection must retry (see `markPendingWithRetry`, `tests/daemon-issue-polling.test.ts:1866`).
- **Hot reload removes the plan's provider** between Start and claim: skipped per-candidate, visible; never a failed Run.
- **`getProjectIssueSnapshot` omits `issue_created_at`** (`run-store.ts:2740`): irrelevant here, don't "fix" it.
- **Resolver now also affects State Advance**: slightly beyond the issue's literal "first agent state"; covered by test 2(b). If reviewers want it narrower, drop the `executeStateAdvance` hunk and its test — nothing else depends on it.
- **Fingerprint is a whole-file hash** (comment edits invalidate previews): acceptable false-positive; refusal message says "reload the preview".
- **Codex review cascades** (repo memory): fixes in pre-provider claim/workspace code surface adjacent P1s per push; keep the claim-boundary diff minimal and DEFER unrelated findings.
