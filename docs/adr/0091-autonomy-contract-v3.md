# Autonomy contract v3: give the agent an explicit memory budget

Symphonika bumps the autonomy preamble to `autonomy-preamble-v3` and adds a fifth contract point after a Routine Firing killed itself on an uncapped build. Firing `01M1CCTRHJT5SV17WQWV3RD7BA` (`refactor-audit`, project esbmc, provider claude) ran `pm-deepen`, which launched `cmake -GNinja ... -DBUILD_TESTING=On -DENABLE_REGRESSION=On -DCMAKE_BUILD_TYPE=RelWithDebInfo` followed by a bare `ninja -C build` — no `-j` cap — on a 24-core host. Thirty-four minutes in, the kernel reported `oom-kill:constraint=CONSTRAINT_MEMCG, oom_memcg=.../symphonika-providers.slice, task=cc1plus` with `memory: usage 33554432kB, limit 33554432kB` and slice `anon 24080453632`; the scope peaked at 22.6G. `OOMPolicy=kill` (ADR 0089) group-killed the whole scope, provider process included, so the firing ended `process_exit_signal_SIGKILL` with no Routine Outcome Claim and no PR. Every mechanism worked as designed: ADR 0064's slice split confined the blast radius, ADR 0089's `MemoryMax=` killed rather than stalled, and ADR 0088's disk-backed scratch was already live. The gap was upstream of all of them — nothing in the preamble ever told the agent a budget existed, so it had no reason to cap `-j`, no reason to prefer a release build over one carrying debug info, and no reason to read its own two-minute `git commit` stall as memory pressure rather than the "slow pre-commit hook or a lock" it recorded in its transcript. The v3 contract therefore tells the agent (a) spawned providers usually share one memory cap across every concurrent attempt, and exceeding it OOM-kills whole process trees — possibly a peer attempt's rather than its own, since the cap is on the shared slice and the kernel picks the victim; (b) build parallelism must be capped explicitly and sized for the share actually available rather than for the whole machine, with debug info skipped when nothing will read a backtrace and only the needed targets built; (c) scratch belongs under `$TMPDIR`, which ADR 0088 sets aside and cleans up per attempt, because a hardcoded `/tmp/...` path escapes that and on a tmpfs `/tmp` spends memory from the same budget; (d) a multi-minute silent stall deserves weighing against memory pressure alongside the usual suspects. Each point is hedged rather than absolute: `src/lifecycle/process-scope.ts` probes `systemd-run --user` once and returns the unwrapped command when it is unusable (ADR 0064), so on non-systemd hosts, containers, and CI there is no cap at all; and ADR 0088 notes an operator who has put their state root on a tmpfs "gains nothing from this change". Stating either unconditionally would ship a falsehood to every agent on those hosts. ADR 0017's v1 invariants and ADR 0043's v2 additions remain valid and are restated verbatim in v3; this ADR extends them rather than supersedes them. The preamble version in `prompt-metadata.json` remains the evidence-replay signal for distinguishing v2 from v3 attempts. This is prompt-level guidance only — no cgroup limit, dispatch gate, or watchdog threshold changes, and ADR 0089's position that host memory pressure is the kernel's problem is unaffected.
