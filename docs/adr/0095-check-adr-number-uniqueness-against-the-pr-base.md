# Check ADR number uniqueness against the pull-request base

ADRs keep their four-digit sequential filename prefixes, but pull-request CI rejects a branch whose contribution would make any prefix ambiguous after merge. The check compares the ADR counts at the branch's merge base and `HEAD`, applies that branch delta to the current pull-request base, and fails when a positive delta produces more than one file for a number. This catches a number selected from a stale base while allowing count-neutral renames and every historical collision that the branch did not worsen.

The existing duplicates are deliberately grandfathered rather than renumbered: their bare-number citations cannot be updated reliably while each number is already ambiguous, whereas their filename slugs still identify them. References to a duplicated historical decision should therefore link its full filename. Allocating numbers only at merge would remove the race but requires a merge-time mutation mechanism, while dropping prefixes would churn every filename and existing citation; this forward-only CI check is the smallest change that catches stale-base allocations and composes with either future policy.

The `main` branch ruleset requires the GitHub Actions `ADR numbers` check with strict required-status-check policy. A pull request must therefore be tested against the latest `main` before it can merge, invalidating an earlier green result after the base advances. A merge queue would provide the same serialization without making authors update their branches, but GitHub limits merge queues to organization-owned repositories and `pmatos/symphonika` is user-owned. `.github/rulesets/main.json` records the complete repository ruleset payload, including the pre-existing deletion and non-fast-forward protections, and `npm run configure:main-ruleset` applies it to the existing named ruleset.
